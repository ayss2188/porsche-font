## v4.4.5

> 一批修复与性能（PID 1 视角校验、500 倍提速、OTA 提示、更新流程修复），外加新功能：字体预览 + 字体属性面板。

### 🖼 字体海报（分享用）

字体属性右上角「海报」，或字体卡片 ⋯ 菜单里的「分享海报」：
把字体本身做成一张竖版图（1080×1440），存到相册。

设计上刻意只放三样东西：**大字、字体名、小字署名** ——
不放字形数、覆盖度这类技术数据（那是给自己看的，不是给别人看的）。
- 大留白，文字靠下不居中
- 深色 / 浅色两种背景，随便切
- 示例文字可以自己改，最多两行，放不下自动缩字号
- 保存后自动通知相册刷新，去「相册 → Pictures」就能看到

### ⚖️ A/B 对比（切换前先看一眼）

点「应用这个字体」时，如果当前已经有别的字体在生效，
会先弹一个对比页：**左边是现在的、右边是要换成的**，同一段文字并排。

- 一个滑块**同时控制两边**，方便比同一字重下的差别
- 对比页里就能确认切换，不用退回去再点一次
- 勾「以后不再提示」就不再打扰（存在本机）
- 当前是「无字体」或重新应用同一个字体时**不会弹**

### 👁 导入前预览（选完文件就能看效果）

以前要「导入 → 打开字体库 → 点 ⋯ → 字体属性」才能看到效果，现在选完文件**立刻**渲染：

- **多选用一行下拉切换**（文件多也不会把顶部撑爆；只有一个文件时这行自动隐藏）
- **粗细滑块**：可变字体能真调字重；静态字体会置灰并说明"装到系统里也不会变"
- 预览区**点一下可以换自定义文字**
- 文件清单默认折叠，显示「已选 3 / 3 个」；每一项带 `中文✓ / 中文✗`
- 可以**单独取消**某个文件（不想导入的就不导）
- 预览失败（比如 `.ttc` 合集）会说明原因，但**仍然可以导入**

技术上：文件的解析和渲染全在浏览器里完成（`FontFace` + 自己读 ttf 表），
**不经过 shell、不复制到设备、不占空间**，关掉就释放。

### 🩺 诊断界面重排成三段

以前「一键上报 / 完整报告」和一堆说明混在一起，看不出层次。现在分成三段，
原来的 **4 个入口一个都没少**：

```
① 状态自检      ✅ 一切正常 · 99 个槽位已生效 · 无冲突
② 快速通道      一键上报 / 连接自检 / 导出小报告
③ 完整报告      查看 / 生成完整报告（5~6 分钟）
```

**① 状态自检**是新增的：只读 `fontctl status` 的现成输出，
把已有字段翻译成一句人话，最多再列 3 条提示：
模块被停用 / 还没有应用字体 / 有槽位没生效 / 同名冲突 / 系统更新过。
它**不发起任何新检测、不联网、不读大文件**。

### ⚠️ 已知限制：有些 ROM 的锁屏时钟不跟字体变

实测案例：ColorOS（OPPO PMA120 / Android 17，用户报告 + 多轮验证）

ColorOS 的「个性化时钟」由
`/system_ext/app/KeyguardPersonalityClocks/KeyguardPersonalityClocks.apk` 渲染，
这个 APK **自带一套装饰字体**（香蕉宽笔刷、Galada、汉仪神奇图鉴…），
不读 `/system/fonts`。所以锁屏时钟的数字**不会**跟随任何字体模块变化，
换多少个时钟样式都一样。

同一份报告也证明模块本身工作正常：

- 99 / 99 个槽位全部替换成功
- 连 44.8 MB 的 `OSans-Solid-Digits-VF.ttf` / `Oplus-Serif.ttf` 都已换成用户字体
  （报告里能看到文件大小与硬链接数）

**取代做法**：不折腾它的 APK（改内容必然签名校验失败，重签需要厂商密钥），
如实告知用户这是系统机制，并在报告里把证据列清楚。

### 🔍 诊断新增「锁屏 / 时钟字体专项」

报告里多一节，专门回答"时钟为什么不变"：

```
── 锁屏 / 时钟字体专项 ──
① 名字带 clock/time/digit/keyguard 的字体（在不在计划里）：
    /system/fonts/AndroidClock.ttf （4 KB）  本次替换：是
② overlay / 主题 APK 里打包了字体（这类字体改 /system/fonts 无效）：
    /system_ext/app/KeyguardPersonalityClocks/KeyguardPersonalityClocks.apk
      → Banana_Wide_Brush_Inspiration.ttf Galada-Regular.ttf …
③ 时钟/字体相关设置：
    [system] keyguard_clock_theme_type=0
    [system] font_variation_settings=4292
④ 相关系统包：com.oplus.systemui …
```

同时修掉了两个自查出来的问题：
- 探测段原来跑在"计划计算"之前，导致「本次替换」恒为「否」—— 已挪到计划之后
- 上一版把「自动发现 / PID 1 校验 / 厂商目录表」误插进了
  「检测到个性化字体才执行」的分支里，ColorOS 那台直接整段跳过 —— 已提到顶层

开：那份也换成你的字体，设置里的选择会失效。
关：只换系统字体。
```

### 🔍 诊断报告：自动发现「没收录」的字体目录和字体名

以前靠人工猜目录，永远有遗漏（云端报告样本少，新机型只能等用户反馈）。

现在报告里会用一次**限深 find（跳过缓存类目录、8 秒超时）**把机器上
"有字体、但不在已知清单里"的目录挖出来，再跟 `targets` 名单比对，
列出"设备上有、名单里没有"的字体名：

```
★ 自动发现：1 个目录有字体、但不在已知清单里
    /data/vendor_x/fonts —— 2 个字体：NewFontA.ttf NewFontB.ttf
★ 设备上有、targets 名单里没有的字体名：
    CustomSans-Regular.ttf …
```

**只读**：不读内容、不算哈希、不改任何文件。以后补目录不用再猜。

### 🔬 从 PID 1 的视角校验「框架到底读到哪个文件」

以前的校验：
- 自挂载模式比 inode（我们挂的和系统原来的 inode 相同 → 算成功）
- 元模块模式比文件大小

两者证明的都是「**我们这边挂上了**」。但框架（`system_server`）是 **PID 1 的子进程**，
它看的是 PID 1 的挂载命名空间 —— 我们这边看得见，不等于框架看得见。

现在诊断报告里多一段：

```
PID 1 视角校验：计划里 148 个槽位中，148 个在 PID 1 的挂载表里可见，0 个看不到
```

或者：

```
PID 1 视角校验：计划里 148 个槽位中，145 个可见，3 个看不到
   看不到的：/system/fonts/MiClock.ttf /my_product/fonts/MiSansVF.ttf …
   → 若同时有条目显示「生效」，就说明挂载对当前 shell 可见、对框架不可见。
```

实现很轻：把挂载计划里的目标路径，与 `/proc/1/mountinfo` 的挂载点做一次比对
（单次 awk，两个文件各扫一遍）。**只读**，不挂载、不写文件。
元模块模式下挂载不是我们做的，这段会自动跳过。

### ⚡ 性能：修掉一个会拖慢诊断的隐患

「永不替换名单」（粗细调节族引用的字体 + `targets/protect.list`）需要解析字体配置。
最初的写法是**每次判定都重新解析**，而判定是在**每个子 shell** 里跑的 ——
槽位一多就是几百次全量解析。

现在改成：扫描阶段算一次、写成 `scanned/skip.list`（小文件，一行一个名字），
判定时只读这个小文件。

实测（200 次判定）：

| | 耗时 |
|---|---|
| 改前（每次重新解析 XML） | **约 84 秒** |
| 改后（读缓存文件） | **0.16 秒** |

约 **500 倍**。判据结果完全一致（沙箱里逐条对过：可变窄体/阿拉伯/主字体 → 不替换，
通用拉丁 → 照常替换）。

### 🐞 修「装完了还显示正在解包中、重启按钮不出现」

真机反馈：点「下载并安装」后，管理器明明装完了，界面却一直卡在
「正在安装中…（管理器还在解包，请勿退出）」，红色重启按钮也不出现。

**根因**：安装完成后要做一次"版本号核实"，而我写的路径里用了一个
**在主项目里根本没有定义的常量** —— 路径实际展开成
`/data/adb/modules_update/undefined/module.prop`，永远读不到 →
于是白等 60 秒 → 最后还报"安装没完成"。

三处一起改了：

1. **模块 id 从 `MODDIR` 推导**（两个项目通用），不再依赖那个未定义的常量
2. **安装器返回 0 就是权威信号**：版本核实只等 **6 秒**（3×2 秒）；
   核不上也照常算完成，只在文案里说明情况 ——
   绝不再让"已完成"看起来像"还在解包"
3. 收尾时**替换掉那条 sticky 的"正在下载并安装"提示**（之前会和进度文字叠在一起抢位置）

另外：`verify` 阶段不再算「安装完成」；顺手去掉了一行重复的 `updRunning = false;`。

### 🔔 系统 OTA 之后会提示「请重新应用」

应用字体时会记下当时的系统构建指纹（`ro.build.fingerprint`）。
系统更新（OTA）后 `/system/fonts` 会被换成新版本，我们的挂载可能对不上新文件，
表现就是"界面显示生效、字体却不对"。

现在指纹一变：

- WebUI 顶部出现横幅：「系统更新过（构建指纹已变），本模块的字体可能没有完全生效…」
- 诊断报告里也会写明两次指纹的差异

不改任何东西，只是**把原因说清楚**，省掉一轮排查。

### 👁 字体预览

字体库里每个字体（**不需要是当前生效的那个**）都能直接看效果：

- 点字体卡片的「⋯」→「预览效果」
- 上面是预览区，下面是输入框 —— 输入什么就实时渲染什么
- 自带几组样例：中英混排 / 英文 / 数字 / 日文 / 韩文 / 符号，一点就换

实现上有个取舍值得说明：字体文件通过 **`FontFace` + ArrayBuffer** 加载，
而不是转成 base64 塞进界面 —— 后者对十几 MB 的字体既慢又吃内存。
临时文件用完立刻删除，同一次会话里重复打开是瞬开（字体已缓存在内存）。

**性能**：这是纯用户主动触发的操作（一次 `cp` + 一次 fetch），
不参与开机、不参与切换字体、不影响模块体积。看 100 遍也不会拖慢启动。

### 🈶 「这个字体支持什么」

导入字体时本来就要探测一遍（读 `cmap` 判断有没有对应字形），
以前这个结论只用来决定"要不要替换"，用户看不到。现在预览页里直接列出来：

```
支持      英文/数字 · 简体中文 · 繁体中文 · 日文假名
不支持    韩文
字形数    23645
类型      可变字体（带字重/宽窄轴）
文件大小  9.4 MB
```

字体卡片上也会多一个小标签（`全语种` / `中文` / `英文`），
扫一眼就知道这个字体能不能顶中文 —— 不用先应用再发现"中文没变"。

`/system_ext/app/KeyguardPersonalityClocks/KeyguardPersonalityClocks.apk` 渲染，
这个 APK **自带一套装饰字体**（香蕉宽笔刷、Galada、汉仪神奇图鉴…），
不读 `/system/fonts`。所以锁屏时钟的数字**不会**跟随任何字体模块变化，
换多少个时钟样式都一样。

同一份报告也证明模块本身工作正常：

- 99 / 99 个槽位全部替换成功
- 连 44.8 MB 的 `OSans-Solid-Digits-VF.ttf` / `Oplus-Serif.ttf` 都已换成用户字体
  （报告里能看到文件大小与硬链接数）

**取代做法**：不折腾它的 APK（改内容必然签名校验失败，重签需要厂商密钥），
如实告知用户这是系统机制，并在报告里把证据列清楚。

### 🔍 诊断新增「锁屏 / 时钟字体专项」

报告里多一节，专门回答"时钟为什么不变"：

```
── 锁屏 / 时钟字体专项 ──
① 名字带 clock/time/digit/keyguard 的字体（在不在计划里）：
    /system/fonts/AndroidClock.ttf （4 KB）  本次替换：是
② overlay / 主题 APK 里打包了字体（这类字体改 /system/fonts 无效）：
    /system_ext/app/KeyguardPersonalityClocks/KeyguardPersonalityClocks.apk
      → Banana_Wide_Brush_Inspiration.ttf Galada-Regular.ttf …
③ 时钟/字体相关设置：
    [system] keyguard_clock_theme_type=0
    [system] font_variation_settings=4292
④ 相关系统包：com.oplus.systemui …
```

同时修掉了两个自查出来的问题：
- 探测段原来跑在"计划计算"之前，导致「本次替换」恒为「否」—— 已挪到计划之后
- 上一版把「自动发现 / PID 1 校验 / 厂商目录表」误插进了
  「检测到个性化字体才执行」的分支里，ColorOS 那台直接整段跳过 —— 已提到顶层

### 🔍 诊断报告：自动发现「没收录」的字体目录和字体名

以前靠人工猜目录，永远有遗漏（云端报告样本少，新机型只能等用户反馈）。

现在报告里会用一次**限深 find（跳过缓存类目录、8 秒超时）**把机器上
"有字体、但不在已知清单里"的目录挖出来，再跟 `targets` 名单比对，
列出"设备上有、名单里没有"的字体名：

```
★ 自动发现：1 个目录有字体、但不在已知清单里
    /data/vendor_x/fonts —— 2 个字体：NewFontA.ttf NewFontB.ttf
★ 设备上有、targets 名单里没有的字体名：
    CustomSans-Regular.ttf …
```

**只读**：不读内容、不算哈希、不改任何文件。以后补目录不用再猜。

### 🔬 从 PID 1 的视角校验「框架到底读到哪个文件」

以前的校验：
- 自挂载模式比 inode（我们挂的和系统原来的 inode 相同 → 算成功）
- 元模块模式比文件大小

两者证明的都是「**我们这边挂上了**」。但框架（`system_server`）是 **PID 1 的子进程**，
它看的是 PID 1 的挂载命名空间 —— 我们这边看得见，不等于框架看得见。

现在诊断报告里多一段：

```
PID 1 视角校验：计划里 148 个槽位中，148 个在 PID 1 的挂载表里可见，0 个看不到
```

或者：

```
PID 1 视角校验：计划里 148 个槽位中，145 个可见，3 个看不到
   看不到的：/system/fonts/MiClock.ttf /my_product/fonts/MiSansVF.ttf …
   → 若同时有条目显示「生效」，就说明挂载对当前 shell 可见、对框架不可见。
```

实现很轻：把挂载计划里的目标路径，与 `/proc/1/mountinfo` 的挂载点做一次比对
（单次 awk，两个文件各扫一遍）。**只读**，不挂载、不写文件。
元模块模式下挂载不是我们做的，这段会自动跳过。

### ⚡ 性能：修掉一个会拖慢诊断的隐患

「永不替换名单」（粗细调节族引用的字体 + `targets/protect.list`）需要解析字体配置。
最初的写法是**每次判定都重新解析**，而判定是在**每个子 shell** 里跑的 ——
槽位一多就是几百次全量解析。

现在改成：扫描阶段算一次、写成 `scanned/skip.list`（小文件，一行一个名字），
判定时只读这个小文件。

实测（200 次判定）：

| | 耗时 |
|---|---|
| 改前（每次重新解析 XML） | **约 84 秒** |
| 改后（读缓存文件） | **0.16 秒** |

约 **500 倍**。判据结果完全一致（沙箱里逐条对过：可变窄体/阿拉伯/主字体 → 不替换，
通用拉丁 → 照常替换）。

### 🐞 修「装完了还显示正在解包中、重启按钮不出现」

真机反馈：点「下载并安装」后，管理器明明装完了，界面却一直卡在
「正在安装中…（管理器还在解包，请勿退出）」，红色重启按钮也不出现。

**根因**：安装完成后要做一次"版本号核实"，而我写的路径里用了一个
**在主项目里根本没有定义的常量** —— 路径实际展开成
`/data/adb/modules_update/undefined/module.prop`，永远读不到 →
于是白等 60 秒 → 最后还报"安装没完成"。

三处一起改了：

1. **模块 id 从 `MODDIR` 推导**（两个项目通用），不再依赖那个未定义的常量
2. **安装器返回 0 就是权威信号**：版本核实只等 **6 秒**（3×2 秒）；
   核不上也照常算完成，只在文案里说明情况 ——
   绝不再让"已完成"看起来像"还在解包"
3. 收尾时**替换掉那条 sticky 的"正在下载并安装"提示**（之前会和进度文字叠在一起抢位置）

另外：`verify` 阶段不再算「安装完成」；顺手去掉了一行重复的 `updRunning = false;`。

### 🔔 系统 OTA 之后会提示「请重新应用」

应用字体时会记下当时的系统构建指纹（`ro.build.fingerprint`）。
系统更新（OTA）后 `/system/fonts` 会被换成新版本，我们的挂载可能对不上新文件，
表现就是"界面显示生效、字体却不对"。

现在指纹一变：

- WebUI 顶部出现横幅：「系统更新过（构建指纹已变），本模块的字体可能没有完全生效…」
- 诊断报告里也会写明两次指纹的差异

不改任何东西，只是**把原因说清楚**，省掉一轮排查。

### 👁 字体预览

字体库里每个字体（**不需要是当前生效的那个**）都能直接看效果：

- 点字体卡片的「⋯」→「预览效果」
- 上面是预览区，下面是输入框 —— 输入什么就实时渲染什么
- 自带几组样例：中英混排 / 英文 / 数字 / 日文 / 韩文 / 符号，一点就换

实现上有个取舍值得说明：字体文件通过 **`FontFace` + ArrayBuffer** 加载，
而不是转成 base64 塞进界面 —— 后者对十几 MB 的字体既慢又吃内存。
临时文件用完立刻删除，同一次会话里重复打开是瞬开（字体已缓存在内存）。

**性能**：这是纯用户主动触发的操作（一次 `cp` + 一次 fetch），
不参与开机、不参与切换字体、不影响模块体积。看 100 遍也不会拖慢启动。

### 🈶 「这个字体支持什么」

导入字体时本来就要探测一遍（读 `cmap` 判断有没有对应字形），
以前这个结论只用来决定"要不要替换"，用户看不到。现在预览页里直接列出来：

```
支持      英文/数字 · 简体中文 · 繁体中文 · 日文假名
不支持    韩文
字形数    23645
类型      可变字体（带字重/宽窄轴）
文件大小  9.4 MB
```

字体卡片上也会多一个小标签（`全语种` / `中文` / `英文`），
扫一眼就知道这个字体能不能顶中文 —— 不用先应用再发现"中文没变"。
